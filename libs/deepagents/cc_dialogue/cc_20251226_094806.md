### 1. 为什么 uv 会这么做？（工具哲学）

`uv sync` 的设计目标是：**“让你的环境完全匹配你的项目定义”**。

如果不把当前项目安装进去，就会出现以下悖论：
*   你的 `pyproject.toml` 里定义了 `name = "deepagents"`。
*   你在写单元测试（比如在 `tests/` 目录下）时，需要 `import deepagents`。
*   如果 `uv sync` 只装了第三方库（比如 langchain），没装你自己。
*   当你运行 `pytest` 时，就会报错 `ModuleNotFoundError: No module named 'deepagents'`。

为了避免你每次 `sync` 完还得手动敲一遍 `pip install -e .`，`uv` 直接把这两步合并了：只要它检测到这是一个 **Application** 或 **Library** 项目（即有 `[project]` 表），它就默认你肯定要在环境里用自己的代码，所以自动帮你做了“可编辑安装”。

### 2. 它是怎么知道要这么做的？（技术标准）

这背后依赖的是 Python 的 **PEP 517 / PEP 518** 和 **pyproject.toml** 标准。

当你运行 `uv sync` 时，它会检查你的 `pyproject.toml` 文件：

```toml:pyproject.toml
[project]
name = "deepagents"  <-- 关键点 1：我有名字
version = "0.3.1"
# ...
[build-system]       <-- 关键点 2：我有构建系统
requires = ["setuptools>=73.0.0", "wheel"]
build-backend = "setuptools.build_meta"
```

*   **识别**：`uv` 看到这些配置，确认“这是一个标准的 Python 包项目”。
*   **决策**：既然这是一个包项目，那么在开发环境里，开发者肯定希望 `import deepagents` 能直接指向源码。
*   **执行**：于是它自动执行了等同于 `pip install -e .` 的逻辑，生成了那个快捷方式（`.pth` 文件）。

### 3. 如果我不想要这个行为怎么办？

虽然这是默认的最佳实践，但如果你真的不想把当前项目装进去（比如你只是在用这个目录管理一堆脚本，而不是开发一个包），你可以在 `pyproject.toml` 里配置或者通过参数告诉 `uv` 这是一个非打包项目。

但在你的场景下（你在开发一个名为 `deepagents` 的库），这个默认行为正是你最需要的。它确保了你的测试代码、示例脚本、Jupyter Notebook 都能无缝地找到你的源码。

**总结：**
这是一种**“约定优于配置”**（Convention over Configuration）的现代工程实践。工具假设你是一个正常的开发者，想在开发环境里测试自己的代码，所以它自动帮你把“网线”接好了。
