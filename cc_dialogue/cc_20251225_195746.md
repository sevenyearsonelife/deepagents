根据你的具体使用场景，有两种主要方式：

如果你只是想在这个库的目录下运行代码或测试，其实**不需要显式安装**。

1.  进入库目录：
    ```bash
    cd libs/deepagents
    ```
2.  使用 `uv` 进行可编辑安装：
    ```bash
    uv pip install -e .
    ```
    *   `-e` (editable) 表示以“可编辑模式”安装。你对源码的任何修改都会立即生效，无需重新安装。
    *   这会将其安装到当前目录的 `.venv` 中。

---

### 场景二：让 CLI (`deepagents-cli`) 使用本地的 `deepagents`
这是最常见的情况：你想修改核心库的代码，并立即在 CLI 工具中测试效果，而不是使用 PyPI 上已发布的版本。

由于本项目各子库是**独立管理**依赖的（每个子库都有自己的 `uv.lock`），你需要修改引用者的配置：

1.  打开 **`libs/deepagents-cli/pyproject.toml`**。
2.  找到 `dependencies` 部分，将 `deepagents` 的版本号引用改为**本地路径引用**：

    **修改前：**
    ```toml
    dependencies = [
        "deepagents>=0.1.0",
        # ...
    ]
    ```

    **修改后：**
    ```toml
    dependencies = [
        "deepagents @ { path = "../deepagents", editable = true }",
        # ...
    ]
    ```
    *(注：如果使用标准 `pip` 或旧版工具，写法可能是 `deepagents @ file:///${PROJECT_ROOT}/libs/deepagents`，但 `uv` 支持上述 path 语法或直接在开发环境中操作)*

3.  然后更新 CLI 的环境：
    ```bash
    cd libs/deepagents-cli
    uv sync
    ```

这样，CLI 就会直接使用你本地 `libs/deepagents` 目录下的代码，你的任何修改都会实时反映在 CLI 的运行中。

### 问题 4
用户：libs文件夹下为何会有多个仓库？  
助手：这种结构通常被称为 **Monorepo（单体仓库）** 模式下的 **多包架构 (Multi-package Architecture)**。

在 `libs/` 下放置多个看似独立的“仓库”（实际上是独立的 Python 包），主要是出于 **解耦** 和 **依赖管理** 的考量。

具体针对 `deepagents` 项目，这样划分有以下几个核心原因：

### 1. 核心与工具分离 (保持 Core 轻量化)
*   **`libs/deepagents` (核心库)**：
    *   这是项目的“大脑”。它只包含最基础的类、逻辑和接口。
    *   **目的**：让那些只想在代码中引用 `deepagents` SDK 的开发者（比如集成到 Django/Flask 后端），可以只安装这个包，而**不需要**下载 CLI 所需的沉重依赖（如终端UI库 `rich`、`prompt_toolkit` 等）。
*   **`libs/deepagents-cli` (命令行工具)**：
    *   这是项目的“手脚”。它依赖于核心库，提供了终端交互界面。
    *   它包含大量与用户交互相关的依赖，这些对于只需要 SDK 的用户是多余的。

### 2. 依赖隔离 (Dependency Isolation)
每个子目录都有自己的 `pyproject.toml` 和 `uv.lock`：
*   **避免冲突**：`acp` 服务可能需要 `fastapi` 的某个特定版本，而 `harbor` 可能依赖另一个不兼容的库。将它们拆开，各自管理依赖，可以避免“依赖地狱”。
*   **安全与体积**：`libs/acp` (Agent Control Protocol) 是服务端组件，可能包含网络服务相关的依赖。普通用户在本地运行 Agent 时并不需要安装这些服务端组件。

### 3. 独立版本与发布周期
*   **核心库** 可能很稳定，版本号更新较慢（如 `v0.1.0` -> `v0.1.1`）。
*   **CLI 工具** 可能频繁调整交互体验，版本号更新很快（如 `v0.5.0` -> `v0.6.0`）。
*   拆分后，团队可以单独发布 `pip install deepagents-cli` 的更新，而无需重新发布核心库。

### 4. 架构清晰度
根据你的目录结构：
*   **`deepagents`**: 定义标准、协议、核心逻辑。
*   **`deepagents-cli`**: 负责本地开发体验、调试。
*   **`acp`**: 负责对外提供标准化的 API 服务接口。
*   **`harbor`**: 负责与其他平台或生态的集成。

**总结：**
这是一种高级的工程实践。它允许你在一个 Git 仓库中管理所有代码（方便代码共享和重构），同时在发布时又能像微服务一样，把它们作为独立的组件（Package）提供给用户，做到“按需安装”。

### 问题 5
用户：我看到很多大公司都有单体仓库，这就是单体仓库么？  
助手：是的，这正是**单体仓库 (Monorepo)** 的一种典型实现形式。

虽然它规模可能不如 Google 或 Meta 那样庞大（它们将全公司所有项目都放在一个 Repo 中），但在开源界和现代软件工程中，这种 **"Workspace-based Monorepo"**（基于工作区的单体仓库）非常流行。

### 为什么这就是单体仓库？

判断一个项目是否为 Monorepo，主要看它是否符合以下特征，而你的项目完全符合：

1.  **统一的代码版本控制 (Single Git Repository)**
    *   `deepagents`、`deepagents-cli`、`acp`、`harbor` 等多个逻辑上独立的项目（Package），物理上都存放在**同一个 Git 仓库**中。
    *   你不需要 `git clone` 四次，一次操作就能获得全貌。

2.  **多包管理 (Multi-Package Management)**
    *   你在 `libs/` 下看到了多个 `pyproject.toml`。
    *   这说明它们是独立构建、独立发布的，但被集中管理。这与将所有代码混在一个 `src/` 里的传统单体应用（Monolith）有本质区别。

3.  **共享基础设施与规范**
    *   虽然每个库有自己的 `Makefile`，但根目录下通常会有统一的说明（如 `README.md`），并且它们遵循相同的编码规范（如 `Always Applied Workspace Rules` 中提到的统一使用 `uv`、`ruff`、Conventional Commits 等）。
    *   如果 `deepagents` 核心库更新了接口，你可以立即在同一个 PR 中修改 `deepagents-cli` 适配它，保证原子性提交（Atomic Commit），这是 Monorepo 最大的优势之一。

### 它属于哪种 Monorepo？

在 Python 生态中，这通常被称为 **Workspace Pattern**（类似 JavaScript 里的 Yarn/npm Workspaces）。

*   **特点**：
    *   使用统一的工具链（这里是 `uv`）。
    *   支持本地路径引用（如 CLI 直接引用本地的 Core 库）。
    *   虽然是 Monorepo，但模块间依然保持了清晰的边界。

**总结：**
是的，这是一个标准的、现代化的 Python Monorepo。它既享受了单体仓库带来的**协作便利性**（统一版本、原子提交、代码复用），又保留了微服务/多库架构的**模块化优势**（独立发布、依赖隔离）。很多知名开源项目（如 LangChain、LlamaIndex 等）目前都采用这种结构。
